      Case study: Theater zone startup
      
        
      
          A multi-device theater is the clearest reason to read profiles — not only to “make the zone work in the UI,”
          but to understand timing, state gates, the control backbone (host + extenders), and what the
          homeowner experiences on a real On / Off.
        
      
      
      

      
      
        
      The problem
      
        
      
          Many configs are signed off when sources switch and power toggles in the app. The end user lives with something else:
          accidental zone Off, On again too fast, processor still booting, display still warming, speakers already “on,”
          drapes moving, masking changing — and a black or silent room for a minute while the UI already says active.
        
      
        
      
          UI active ≠ path ready. Profile delays and zone logic decide when picture and sound are actually good.
        
      
      
      

      
      
        
      Control backbone (host + extender)
      
        
      
          Device profiles define what to send. The Savant host and control extenders decide where those
          commands leave the system. Theater gear is not controlled in isolation.
        
      
        
      
          
            
      
              Piece
              Example
              Role in the theater
            
      
                
          
            
      
              Host
              Pro Host (SVR-xxxx)
              Runs Blueprint: services, state, triggers, Automator workflows, UI. Owns timing logic and LTC lighting/shades when used.
            
      
            
      
              Control extender
              SmartControl 12 (SSC-0012)
              Network I/O brick: RS-232, IR, GPIO, relays. Host assigns device control paths to these ports.
            
      
            
      
              Endpoints
              Main processor, Meridian speakers, display, sources, drapes, masking
              Profiles with Power On waits and preferred transport (IP / RS-232 / IR / contact). Slow path (main processor + display) still owns “ready.”
            
      
                
        
      
        
      
          Preferable command path:
        
      
        
      
          
      Host evaluates zone / service / workflow / trigger
      
          
      IP devices — host talks on the LAN (may never use an extender)
      
          
      RS-232 / IR / relay devices — host → extender port → copper to the device
      
          
      Profiles supply the bytes, delays, and state gates; extender only provides the jack
      
        
      
        
      
          First-On serial failures are often port binding, baud, or wiring on the extender — not the host “forgetting” Power On.
          IP failures are often subnet, port, or sending commands before the device finished booting.
        
      
      
      

      
      
        
      Example stack (roles only)
      
        
      
          
            
      
              Role
              Typical profile timing
              Why it matters
            
      
                
          
            
      
              AV processor
              ~60 s after wake / WoL
              Main theater processor — routing / profiles; slowest “brain”
            
      
            
      
              Projector / display
              ~40–60 s warm-up
              Image path; input commands often race warm-up
            
      
            
      
              Speaker controller (e.g. Meridian 271)
              ~3 s On / ~2 s Off (standby)
              Zone trigger On when theater active, Off when inactive — not source PowerOn. IP preferred (e.g. TCP 9014). Ready long before processor/display.
            
      
            
      
              Streaming source
              ~3 s
              Fast; not the bottleneck
            
      
            
      
              Movie server source
              ~5 s leave-standby
              Standby vs cold off is different
            
      
            
      
              Drapes (momentary relay)
              ~0.5 s pulse
              Environment via extender relay; not AV power state
            
      
            
      
              Screen masking
              Command + motion time
              Often delayed until stack is up (13 s video + 65 s zone)
            
      
                
        
      
        
      
          Two “processors,” two jobs: the main AV processor owns video/audio routing and source profiles.
          The Meridian-class unit is the speaker / volume path. Do not treat Meridian ready as “theater ready.”
        
      
      
      

      
      
        
      How the theater operates
      
        
      
          When the homeowner turns the theater zone on (or picks a source that activates the zone), the host runs
          parallel paths — not one long serial script.
        
      
        
        
          
      • Zone becomes active — Custom trigger sends Meridian PowerOn (#MSR ON, ~3 s). Same trigger’s Else on inactive sends PowerOff (#MSR SB standby, ~2 s). Drapes open (relay pulse). Optional delayed Fullscreen (~65 s).
        • 
          
      • Source service PowerOn — Automator for that source: source power, main processor LoadProfile / input, display power + input (often non-blocking steps).
        • 
          
      • Video service active — Separate trigger fires Fullscreen after ~13 s (picture position + mask preset) — a deliberate mid–warm-up window (see below).
        • 
        
      
        
      
          Speakers can be up while the picture is still black. That is expected. Judge path ready after the
          main processor + display slow path (~60–65 s), not when Meridian ACKs On.
        
      
      
      

      
      
        
      Layers of startup logic
      
        
      A solid theater On usually splits work like this:
      
        
        
          
      • Zone trigger (ZoneIsActive) — Meridian / speakers On, drapes open, optional processor wake, and a delayed masking action (e.g. ~65 s). On inactive: Meridian Off (standby), drapes close.
        • 
          
      • Source PowerOn workflow — that source’s power, main processor profile/input, display power, display input select.
        • 
          
      • Video trigger (stream / movie server / disc service active) — “Fullscreen” after ~13 s. Often runs before the zone’s 65 s call.
        • 
        
      
        
      
          Zone + source workflow fire near the same time (often non-blocking). “Fullscreen” can fire twice by design.
          Real AV readiness still follows the slowest profiles (main processor + display), not Meridian and not the first mask move.
        
      
        
      
          Why ~13 s for Fullscreen (not ~60 s): After the display Power On is sent, the host often waits on
          projector feedback / profile completion for a long window (on the order of the warm-up — ~60 s). Waiting
          that full cycle before masking is too late for a good room feel. Field testing found a practical window at
          about 13 seconds: the host can still accept and fire a service/zone trigger mid projector
          power-up wait, so picture position + ShadePreset run while the lamp is still coming up — without editing
          the vendor profile’s long Power On delay. Re-check this timing if the projector profile or firmware changes.
        
      
        
      
          What “Fullscreen (16:9)” actually runs: a custom Automator workflow with two non-blocking steps —
          (1) display SetPicturePosition1.85:1 (lens/picture memory), and
          (2) screen controller ShadePreset address 1.1.0, preset 3.
          Service name says 16:9; projector action is 1.85:1. Preset 3 must be taught on the screen controller as the full mask.

      t ≈ 40–60 s — Display warm-up / profile feedback finishing; main processor boot finishing
      
          
      t ≈ 65 s — Same Fullscreen workflow again (zone trigger — re-assert after slow path)
      
          
      Zone inactive — Trigger Else: Meridian PowerOff (standby), drapes close; confirm display/processor Off elsewhere
      
        
      
        
      
          Two paths, one workflow: ~13 s (video source active) and ~65 s (zone active) both call the same Automator —
          display 1.85:1 picture position + screen controller preset 3.
          The 13 s path is intentional: host can fire the trigger during the long projector Power On / feedback wait
          so masking is not stuck behind a full ~60 s profile completion. Second (~65 s) run can re-assert after the slow path.
          Judge true AV readiness after ~60–65 s, not when Meridian is On or the mask first moves.
        
      
      
      

      
      
        
      What profiles teach you (so you can fine-tune)
      
        
        
          
      1. Who is slow — Put zone order and delays around the main processor and display, not around the streamer or Meridian.
        2. 
          
      2. Speaker controller ownership — Meridian On/Off belongs on a zone state trigger, not buried only in one source’s PowerOn. Else branch on inactive is required.
        3. 
          
      3. State gates — Power On may be skipped if Savant thinks the device is already on (Meridian and others). Fast off→on fails here.
        4. 
          
      4. Standby vs off — Meridian Off is often standby (#MSR SB); sources may only leave standby. Full rack cycle is a different path.
        5. 
          
      5. Input mapping / Device ID / login — Meridian notes: logical inputs are unassigned by default. Other profiles may require Device ID or login — treat profile notes as install requirements, not optional reading.
        6. 
          
      6. Momentary vs latched — Drapes pulse; they are not a power state machine like a projector.
        7. 
          
      7. Off path completeness — Zone Off may only close drapes and power Meridian. Confirm display and main processor Off live somewhere, or the room stays lit.
        8. 
          
      8. Transport vs logic — Meridian preferred IP (e.g. port 9014) is host→LAN. RS-232 / IR / contact devices must match Blueprint port assignment on host or extender.
        9. 
        
      
      
      

      
      
        
      Host tools: custom workflows & triggers
      
        
      
          The host is where you go beyond “profile defaults.” Useful patterns for a theater:
        
      
        
        
          
      • Service PowerOn / PowerOff workflows (Automator) — Source-specific chains: power display, LoadProfile on the main processor, set input, non-blocking steps. Keep one workflow per source so HDMI routing stays correct.
        • 
          
      • Zone state triggers — Watch ZoneIsActive: Then → Meridian PowerOn, drapes open (and any room-level cues); Else → Meridian PowerOff, drapes close. Speakers follow the room, not a single source.
        • 
          
      • Service state triggers — Watch a video service ServiceIsActive (stream / movie server / disc) for aspect/masking. After Delay ~13 s on Fullscreen is a field-tuned mid–warm-up window: the host will still run the trigger while the projector profile is in its long Power On / feedback wait (~60 s class).
        • 
          
      • After Delay on actions — Host-side delay (13 s and/or 65 s) without editing vendor projector XML. Prefer this for masking so profile updates do not wipe timing; re-validate 13 s if projector firmware or profile delays change.
        • 
          
      • Shared custom workflows — One “Fullscreen” workflow called from multiple triggers so picture position + shade preset stay in sync.
        • 
          
      • Else branches — Explicit Off/reset when state goes false (Meridian standby, close drapes, mask reset). Missing Else is a common “room never restores” bug.
        • 
        
      
        
      
          Prefer host logic over profile hacks when possible: triggers and Automator survive device profile updates better than hand-edited PowerOn delays inside third-party XML.
        
      
      
      

      
      
        
      How to use Profile Decoder on a job
      
        
        
          
      • Drop each endpoint profile and read Field implications, power max waits, and preferred transport (IP / RS-232 / IR / contact).
        • 
          
      • List the slow path (≥ ~10–15 s) and design zone/workflow delays around it.
        • 
          
      • For RS-232 / IR / relay devices, confirm which host or SmartControl port is assigned in Blueprint — the profile does not name the physical jack.
        • 
          
      • Compare source PowerOn workflows to zone triggers: what is missing on Off? What races warm-up?
        • 
          
      • Use host triggers + Automator for custom timing and environment; edit profiles only when the vendor definition is wrong for the site.
        • 
        
      
        
      
          The goal is not a longer config — it is a zone that survives real use: accidental Off, impatient On, and the first show of the night after a cold rack — with control paths that actually reach the hardware.
